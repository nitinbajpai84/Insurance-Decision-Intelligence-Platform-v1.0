# Insurance ML Feature Engineering

This package adds leakage-safe SQL feature views, physical feature tables, and a Python refresh/validation job for the insurance analytics MVP.

## Files

- `006_ml_feature_engineering_views.sql`: source-of-truth SQL views for all model features.
- `007_ml_feature_tables.sql`: physical feature tables and analytics indexes.
- `008_ml_feature_quality_checks.sql`: SQL row count, null, window, and target distribution checks.
- `009_refresh_ml_feature_tables.sql`: SQL Editor refresh script to populate the physical feature tables from the feature views.
- `010_debug_and_refresh_propensity_features.sql`: optimized propensity diagnostics and monthly refresh script.
- `011_ml_feature_view_diagnostics.sql`: pre-refresh row count diagnostics for all feature views.
- `012_ml_feature_chunk_refresh_helpers.sql`: helper functions for refreshing one table/snapshot or date range at a time.
- `013_one_feature_diagnostics.sql`: one-view-at-a-time diagnostics for SQL Editor timeout scenarios.
- `refresh_ml_feature_tables.py`: refresh orchestration and data quality checks.
- `smoke_test_ml_feature_sql.py`: local static check that table indexes only reference columns exposed by the feature views.
- `ml_feature_quality_report.json`: generated by the Python refresh job.

Each table includes:

- `snapshot_date`

- `target_label`
- `training_window_start`
- `training_window_end`
- `prediction_window_start`
- `prediction_window_end`

## Leakage Prevention

Every view follows an as-of-date pattern:

- Features are calculated from records before `snapshot_date`.
- Labels are calculated from future outcomes starting at `prediction_window_start`.
- `training_window_end` is equal to `snapshot_date`.
- `prediction_window_start` is equal to `snapshot_date`.
- The Python quality job checks that feature and prediction windows do not overlap incorrectly.

This means a training row represents what was known at the snapshot date, not what happened later.

## Supabase Setup

Run the SQL in this order from the Supabase SQL editor or `psql`:

```sql
\i 005_ml_schema_enhancements.sql
\i 006_ml_feature_engineering_views.sql
\i 007_ml_feature_tables.sql
\i 008_ml_feature_quality_checks.sql
\i 009_refresh_ml_feature_tables.sql
```

If the Supabase SQL Editor times out on large refreshes, use:

```sql
\i 011_ml_feature_view_diagnostics.sql
\i 012_ml_feature_chunk_refresh_helpers.sql
select * from public.refresh_ml_feature_snapshot('propensity_to_buy_features', date '2023-01-01');
```

If the combined diagnostics in `011` time out, run one section at a time from `013_one_feature_diagnostics.sql`.

If `005_ml_schema_enhancements.sql` is already applied, start from `006_ml_feature_engineering_views.sql`.

The table creation script uses `create table if not exists`. If you change a view's column list after creating the physical tables, recreate the affected feature table so its structure matches the view.

## Refresh Commands

Refresh all feature tables and run checks:

```bash
python refresh_ml_feature_tables.py --feature all
```

Refresh one table:

```bash
python refresh_ml_feature_tables.py --feature policy_lapse_features
```

Validate existing materialized tables without refreshing:

```bash
python refresh_ml_feature_tables.py --validate-only --feature all
```

Generate a dry-run plan:

```bash
python refresh_ml_feature_tables.py --dry-run --feature all
```

Run SQL checks directly:

```sql
select * from public.v_ml_feature_row_counts;
select * from public.v_ml_feature_required_null_checks;
select * from public.v_ml_feature_window_checks;
select * from public.v_ml_feature_target_distribution;
```

## Data Quality Checks

The Python job writes `ml_feature_quality_report.json` and checks:

- Row counts are greater than zero.
- Required ML columns are present and non-null.
- Training and prediction windows are valid.
- Target labels are populated.
- Classification targets have more than one class where expected.
- Numeric feature null rates are summarized.
- Numeric feature distributions are summarized with min, max, and average.

Warnings are expected for sparse features in early snapshots, but failures should be fixed before model training.

## Notes For Model Training

- Use `snapshot_date` for time-based train/validation/test splits.
- Do not random-split rows across time for lapse, churn, conversion, claim, fraud, or CLV models.
- For ranking models such as next best product and next best customer, group validation by `customer_id` or `agent_id` plus `snapshot_date` to avoid candidate leakage across the same decision event.
- Rebuild feature tables after every new synthetic data load or schema/data generator change.
